# Заметки

## Задача 1. Распределение заказов по филиалам

### Что сделано
- Исправлен баг: в `findNearest` координаты филиала передавались в `distanceKm` в обратном порядке (lon, lat вместо lat, lon).
- Добавлены правила `pickup_point` и `city`; `geo` теперь ищет ближайший филиал внутри города заказа, если там их несколько.
- Дневной лимит: `assignBranch` остаётся чистой функцией, заполненность ей передаёт функция `isFull`. Сутки считаются по Алматы (UTC+5) в `almatyDate`.
- API: `POST /orders/:id/assign` (идемпотентный) и `GET /branches/:id/load?date=...`. Логика вынесена в `service.ts`, `server.ts` только маршрутизирует.
- Тесты на правила, лимит, границу суток по Алматы, идемпотентность.

### Допущения
- Заказ с правилом `manual` лимит не проверяет, но в загрузку филиала засчитывается.
- Если выбранный филиал заполнен, ищется ближайший незаполненный среди всех активных филиалов магазина (не только в городе), правило записывается как `geo`.
- Если у заказа нет координат и выбранный правилом филиал заполнен, результат `unassigned`.
- В `load` при некорректной дате возвращается 400 раньше, чем проверяется существование филиала.

### Что изменилось бы при нескольких экземплярах с общей БД
- Сейчас `assignments` лежит в памяти процесса. У каждого экземпляра был бы свой счётчик, лимит мог бы превышаться, а повторный запрос на другой экземпляр занял бы лимит второй раз.
- Идемпотентность: таблица распределений с уникальным ключом по `order_id`; запись через `INSERT ... ON CONFLICT (order_id) DO NOTHING` и возврат уже существующей строки.
- Лимит: счётчик на (филиал, сутки по Алматы), увеличивать атомарно одним запросом `UPDATE ... SET assigned = assigned + 1 WHERE assigned < daily_limit`, либо в транзакции блокировать строку филиала (`SELECT ... FOR UPDATE`). Проверка и запись должны быть в одной транзакции, иначе два экземпляра одновременно «увидят» свободное место.
- Дату суток по Алматы лучше сохранять в записи при распределении, а не пересчитывать при каждом запросе.

### Что доделал бы
- Валидация и логирование запросов, тесты на HTTP-уровне.
- Подсчёт загрузки без полного перебора заказов (индекс или счётчики).


## Задача 2. Онлайн-запись к мастеру

### Что сделано
- Исправлен баг в `overlaps`: сравнения стали строгими, интервалы полуоткрытые `[start, end)`, запись встык к другой не пересекается.
- `getSlots`: шаг 15 минут, услуга целиком в рабочем времени, не пересекает перерывы и активные записи (отменённые игнорируются), начало строго позже текущего момента (`clock.ts`).
- `GET /masters/:id/slots`, `POST /bookings`, `DELETE /bookings/:id`. Логика в `service.ts`, `server.ts` только маршрутизирует; ошибки через `ApiError(status, code)`.
- Телефон нормализуется в `+7XXXXXXXXXX` (`phone.ts`), время хранится в UTC.
- Защита от двойной записи: очередь по мастеру (`lock.ts`), проверка слота и вставка выполняются внутри одной блокировки.
- Тесты: слоты, создание, отмена, телефон, одновременные запросы.

### Допущения
- Принимаются только казахстанские мобильные номера (коды 70x, 747, 77x); форматы `+7`, `7`, `8`; с плюсом `+8` не допускается. Городские и чужие номера дают 400 `invalid_phone`.
- `start` без часового пояса — 400 `invalid_start`. Время с ненулевыми секундами или не на сетке слотов — 409 `slot_unavailable`.
- Несуществующий мастер или услуга — 404; услуга, которую мастер не оказывает, — 400.
- Отмена ровно за 2 часа до начала разрешена; повторная отмена уже отменённой записи всегда 200, даже если до начала меньше 2 часов.
- Часовой пояс фиксирован (+05:00), как в условии.

### Что изменилось бы при нескольких экземплярах с PostgreSQL
- Блокировка в памяти работает только внутри одного процесса. Два экземпляра сервиса могли бы одновременно записать клиентов на одно время.
- Основная защита должна быть в самой БД: ограничение `EXCLUDE USING gist (master_id WITH =, tstzrange(start_at, end_at, '[)') WITH &&) WHERE (status = 'active')` (нужно расширение `btree_gist`). Конфликт возвращается ошибкой `23P01`, которую сервис превращает в 409. Отменённые записи в ограничение не попадают.
- Альтернатива: транзакция с `pg_advisory_xact_lock(hashtext(master_id))` или `SELECT ... FOR UPDATE` по строке мастера: проверить пересечения и вставить внутри одной транзакции.
- Отмена: один атомарный `UPDATE bookings SET status = 'cancelled' WHERE id = $1 AND status = 'active'`, а правило «за 2 часа» проверять в том же запросе.
- Время хранить как `timestamptz`; слоты считать по тем же правилам в приложении, а БД оставить последним рубежом.

### Что доделал бы
- Проверка размера тела запроса, логирование, тесты на уровне HTTP.
- Очистка записей в `lock.ts` и ограничение числа ожидающих запросов на одного мастера.
- Кэширование слотов и индекс по (мастер, время) в БД.
